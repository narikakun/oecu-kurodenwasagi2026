# 黒詐欺電話 システム設計書

## 1. 文書情報

| 項目 | 内容 |
|---|---|
| システム名 | 黒詐欺電話 |
| 対象機 | 600-A2型 黒電話 |
| 文書種別 | 基本設計書・初版 |
| 作成日 | 2026年10月2日 |
| 開発言語 | Python 3 |
| 実行環境 | Raspberry Pi 5 / Raspberry Pi OS |
| AI音声基盤 | OpenAI GPT-Live API |

## 2. 目的

昔ながらの黒電話の外観と操作感を残したまま、受話器を取るとAIとの音声対話が始まる体験装置を制作する。

AI機器らしい画面や操作を見せず、「普通の古い電話だと思って応対したらAIと対話していた」という意外性を体験の中心に置く。

## 3. 設計方針

### 3.1 採用する方針

- 黒電話は開けて改造してよい。
- 外装、受話器、フックスイッチ、ロータリーダイヤルの操作感を残す。
- 元の電話回線やRJ11端子から信号を読むのではなく、内部の機械接点を直接利用する。
- フックスイッチとダイヤル接点を別々のGPIO入力へ接続する。
- 音声入出力にはUSB-C受話器のマイクとスピーカーを利用する。
- Raspberry Pi 5一台でGPIO入力、音声入出力、AI通信、状態管理を担当する。
- 初期版ではベルを使用しない。
- 電源投入後はアプリケーションを自動起動し、画面やキーボードなしで運用できるようにする。

### 3.2 初期版の対象外

- 黒電話本来のカーボンマイクおよび受話器回路の再利用
- 電話回線への接続
- 元の電磁ベルの駆動
- RJ11外部端子だけを使ったフック・ダイヤル信号の合成検出
- Raspberry Pi Picoとの二台構成
- 映像や画面を用いた操作

ベルは将来拡張とし、必要になった時点で専用駆動回路と安全設計を追加する。

## 5. ハードウェア設計

### 5.1 構成部品

| 区分 | 部品 | 用途 | 必要性 |
|---|---|---|---|
| 本体 | 600-A2型 黒電話 | 外装、フック、ダイヤル | 必須・入手済み想定 |
| 制御 | Raspberry Pi 5 | 全体制御、AI通信 | 必須 |
| 電源 | Pi 5対応公式相当電源 | 本体への安定給電 | 必須 |
| 記憶媒体 | microSDまたはSSD | OS・アプリ保存 | 必須 |
| 音声 | USB-C受話器 | マイク・スピーカー | 必須・入手済み想定 |
| 配線 | ジャンパーワイヤまたは細線 | 接点とGPIOの接続 | 必須 |
| 試作 | ブレッドボード | 配線確認 | 開発時に推奨 |
| 測定 | デジタルテスター | 接点と導通の確認 | 強く推奨 |
| 固定・絶縁 | 熱収縮チューブ、絶縁材、結束材 | 短絡・断線防止 | 必須 |
| 組立 | はんだ、コネクター類 | 本実装の固定 | 実装方法に応じて必要 |

内部の無電圧接点を直接利用する採用構成では、9V電池、PC817、RJ11端子台は原則不要である。ただし、実機確認で接点が既存回路から電気的に分離できない場合は、絶縁回路を再検討する。

### 5.2 GPIO接続

内部接点は「GPIO入力とGNDを短絡する機械スイッチ」として使用し、Raspberry Pi側の3.3V内部プルアップを有効にする。

```text
Raspberry Pi 5

GPIO_HOOK ───────── フックスイッチ接点 ───────── GND

GPIO_DIAL ───────── ダイヤルパルス接点 ───────── GND
```

論理値は次のように扱う。

| 接点状態 | GPIO値 | 論理状態 |
|---|---:|---|
| 開 | HIGH | 非作動 |
| 閉 | LOW | 作動 |

GPIO番号の候補はフックをGPIO17、ダイヤルをGPIO27とする。最終番号は、Pi 5のピン配置、ケース、冷却装置、他の周辺機器との干渉を確認して確定する。

### 5.3 フックスイッチ

- 受話器を上げた状態と置いた状態を検出する。
- 実機によって接点の開閉方向が逆の場合はソフトウェア設定で反転する。
- 機械的なチャタリングを除去するため、状態変化が一定時間継続した場合だけ確定する。
- 初期値として30msのデバウンス時間を採用し、実測後に調整する。

### 5.4 ロータリーダイヤル

600-A2型のダイヤルは、履歴中の教員情報に基づき20パルス/秒を設計上の仮定とする。1周期は約50msである。実機測定で確認後、確定値に更新する。

| ダイヤル値 | 検出パルス数 |
|---:|---:|
| 1～9 | 同じ数 |
| 0 | 10 |

基本処理は次のとおりとする。

1. 有効なパルスエッジを検出する。
2. 短すぎる変化をチャタリングとして除外する。
3. 最後のパルスから一定時間、新しいパルスが来なければ一桁を確定する。
4. 1～9パルスは1～9、10パルスは0へ変換する。
5. 0回、11回以上、規定時間外の列は入力エラーとして破棄・記録する。

桁確定待ち時間の初期値は150msとし、実測波形を基に調整する。

### 5.5 音声入出力

- USB-C受話器をLinux上のUSBオーディオ入力・出力デバイスとして使用する。
- 元の電話用マイクとスピーカーは電気的には使用しない。
- USB-C受話器の機構を黒電話の受話器内へ収め、外見と持ち方を維持する。
- 起動時に指定デバイスが入力・出力の両方で認識されていることを確認する。
- デバイス名は実機確認後に設定ファイルへ登録し、OSの既定デバイス順には依存しない。

### 5.6 電気的安全

- 黒電話を公衆電話回線、PBX、電話用壁面端子へ接続しない。
- GPIOへ5Vを入力しない。GPIOは3.3V系で使用する。
- 接点に既存回路由来の電圧がないことをテスターで確認してから接続する。
- 元のベル、コイル、コンデンサーなどから対象接点を必要に応じて切り離す。
- 可動部に配線が挟まれないよう固定し、露出導体を絶縁する。
- 通電中に内部配線を変更しない。

## 6. ソフトウェア設計

### 6.1 モジュール構成

```text
src/
├── main.py             # 起動、依存関係の組み立て、終了処理
├── config.py           # GPIO、音声、API、時間設定
├── state_machine.py    # システム状態と遷移
├── hook.py             # フックスイッチ監視
├── dial.py             # パルス計数と数字確定
├── audio.py            # USB音声の取得・再生
├── live.py             # GPT-Live接続、音声・イベント処理
├── scenario.py         # 会話指示、ダイヤル操作の意味付け
└── log.py              # 運用ログ
```

ハードウェア未接続でも試験できるよう、GPIO入力、音声入出力、API通信はそれぞれ交換可能なインターフェースとして分離する。

### 6.2 状態モデル

| 状態 | 内容 |
|---|---|
| `BOOTING` | OS・アプリ起動中 |
| `SELF_TEST` | GPIO、音声、ネットワーク、設定の確認中 |
| `IDLE` | 受話器が置かれ、利用待ち |
| `CONNECTING` | 受話器が上がり、APIへ接続中 |
| `CONVERSATION` | AIとの音声対話中 |
| `ENDING` | 音声停止、API切断、後処理中 |
| `ERROR` | 継続不能な異常が発生 |

### 6.3 状態遷移

```text
BOOTING
   ↓
SELF_TEST ──失敗──→ ERROR
   ↓成功
IDLE
   │ 受話器を上げる
   ▼
CONNECTING ──失敗──→ IDLE または ERROR
   │ 接続成功
   ▼
CONVERSATION
   │ 受話器を置く
   ▼
ENDING
   │ 切断・音声停止完了
   └────────────────→ IDLE
```

どの状態でも受話器が置かれたことを最優先イベントとして扱い、会話音声の再生停止とセッション終了を行う。

### 6.4 GPT-Live接続

Raspberry Piは信頼される端末としてAPIキーを保持し、GPT-Liveのサーバー向けプライマリWebSocketへ直接接続する。一つの接続で音声とJSON制御イベントを双方向に送受信する。

```text
接続先: wss://api.openai.com/v1/live/sessions
認証:   Authorization: Bearer $OPENAI_API_KEY
開始:   最初のメッセージとして session.start を送信
```

- APIキーはソースコード、Git、ログへ保存しない。
- systemdの環境ファイルなど、権限を制限した外部設定から読み込む。
- 受話器を上げた時点でWebSocketへ接続し、モデル、会話指示、音声形式、音声を含む`session.start`を送る。
- `session.started`を受信してから音声送信を開始する。
- USBマイクの音声をセッション指定形式へ変換し、`session.input_audio.append`で連続送信する。
- `session.output_audio.delta`の音声差分を到着順にデコードして再生キューへ追加する。
- GPT-Live自身に発話タイミングを判断させ、旧Realtime方式の手動音声コミットや応答開始要求には依存しない。
- 入力音声は会話中を通して送信し、GPT-Liveの同時リスニング・発話を利用する。
- 受話器を置いた場合は、マイク送信と再生を直ちに止め、WebSocketを閉じてセッションを終了する。
- 出力音声の完了通知だけに依存せず、アプリケーション側の再生キューで再生中の音声量を管理する。
- 接続失敗時は短いエラー音または無音終了とし、無限再接続しない。

初期音声形式は公式例と同じモノラルPCM16・24kHzを候補とし、USB受話器の対応形式を確認して確定する。必要なら送受信時にサンプルレートと形式を変換する。

モデル名、音声形式、音声名、会話指示、委譲設定、再接続回数は設定ファイルで変更可能にする。モデルの初期候補は`gpt-live-1`とするが、利用可能性を実装時に確認し、特定のモデル名を処理コードへ固定しない。

### 6.5 ダイヤル入力の用途

初期版ではダイヤル数字を取得してイベントとして記録・通知できるところまでを必須とする。会話中の具体的な機能割り当てはシナリオ設計で確定する。

候補例は次のとおりである。

| 入力 | 機能候補 |
|---:|---|
| 0 | 会話終了または最初からやり直す |
| 1～9 | シナリオ、話題、選択肢の指定 |

誤操作を避けるため、ダイヤル機能は状態ごとに有効・無効を切り替える。

### 6.6 設定項目

| 項目 | 内容 |
|---|---|
| フックGPIO番号 | 使用するBCM GPIO番号 |
| ダイヤルGPIO番号 | 使用するBCM GPIO番号 |
| 入力反転 | 実機の接点方向への対応 |
| デバウンス時間 | 接点ごとのチャタリング除去時間 |
| 桁確定待ち時間 | 最終パルスから数字確定までの時間 |
| 音声入力デバイス | USBマイク識別子 |
| 音声出力デバイス | USBスピーカー識別子 |
| GPT-Liveモデル | 利用するGPT-Liveモデル識別子 |
| GPT-Live音声形式 | 入出力の形式とサンプルレート |
| GPT-Live音声 | AIの音声識別子 |
| GPT-Live委譲設定 | Responses委譲またはクライアント委譲の設定 |
| 会話指示 | AIの役割と対話ルール |
| ログレベル | 通常運用・デバッグの切替 |

## 7. 機能要件

| ID | 要件 |
|---|---|
| F-01 | 受話器の上げ下げを検出できること |
| F-02 | ダイヤル1～9および0を識別できること |
| F-03 | 受話器を上げるとAI音声セッションを開始できること |
| F-04 | USB受話器から利用者の音声を送信できること |
| F-05 | AIの応答音声をUSB受話器から再生できること |
| F-06 | 受話器を置くと再生とセッションを終了できること |
| F-07 | 起動後、手動ログインやコマンド操作なしで待機状態へ移れること |
| F-08 | 検出した数字を会話制御へ渡せること |
| F-09 | 異常発生時に原因をローカルログへ記録できること |

## 8. 非機能要件

| ID | 要件 |
|---|---|
| N-01 | 外部からは通常の黒電話に見えること |
| N-02 | 受話器操作後、可能な限り短時間で反応を開始すること |
| N-03 | 一時的なネットワーク障害でアプリ全体が停止しないこと |
| N-04 | APIキーや会話内容を通常ログへ出力しないこと |
| N-05 | 電源再投入で自動復旧すること |
| N-06 | ハードウェアなしでもダイヤル判定と状態遷移を単体試験できること |
| N-07 | 会話終了後に前利用者のセッション状態を次回へ持ち越さないこと |

## 9. ログ設計とプライバシー

記録するログは、時刻、状態遷移、フックイベント、確定したダイヤル値、API接続結果、エラー種別に限定する。

初期設定では次を記録しない。

- 生のマイク音声
- AIの再生音声
- 会話全文または文字起こし
- APIキー

デバッグのため会話データを保存する必要が生じた場合は、保存目的、保存期間、閲覧権限、利用者への表示を別途決定する。

## 10. 異常時の動作

| 異常 | 動作 |
|---|---|
| USB受話器がない | AI接続を開始せず、エラーを記録して待機 |
| ネットワーク未接続 | 接続を中止し、受話器を置いた後に再利用可能とする |
| API認証失敗 | 再試行を制限し、秘密情報を含めず記録 |
| 会話中の通信切断 | 再生を止め、セッションを破棄して待機へ戻る |
| 不正なダイヤル数 | 入力を破棄し、警告ログだけを残す |
| フック入力が不安定 | デバウンス後も不安定ならエラー扱いにする |
| アプリ例外 | 安全に音声と通信を終了し、systemdで再起動する |

## 11. 開発手順

1. 黒電話を開け、フックスイッチとダイヤルパルス接点を特定する。
2. 電源を接続せず、テスターで各接点の導通変化を確認する。
3. USB-C受話器がPi上で録音・再生できることを確認する。
4. フックスイッチだけをGPIOへ接続し、上げ下げを取得する。
5. ダイヤル接点をGPIOへ接続し、1～0のパルス数を測定する。
6. 実測値を基にデバウンス時間と桁確定時間を決める。
7. モック入力で状態遷移と異常処理を実装・単体試験する。
8. GPT-LiveとのWebSocket接続と音声送受信を単独で確認する。
9. フック、ダイヤル、音声、APIを統合する。
10. systemdによる自動起動と電源再投入試験を行う。
11. 配線を固定・絶縁し、外装を閉じて総合試験を行う。

## 12. 受入試験

| ID | 操作 | 期待結果 |
|---|---|---|
| T-01 | 電源を入れる | 自動起動し、受話器を置いた状態で待機する |
| T-02 | 受話器を上げる | 上げ状態を一度だけ検出し、AI接続を開始する |
| T-03 | 受話器へ話す | 発話がAIへ届き、応答が受話器から聞こえる |
| T-04 | AI応答中に話す | 設計した割り込み動作が行われる |
| T-05 | 1～9を各1回回す | 回した数字と同じ値が一度だけ確定する |
| T-06 | 0を回す | 10パルスを0として一度だけ確定する |
| T-07 | 会話中に受話器を置く | 音声再生とAPI通信が終了し、待機へ戻る |
| T-08 | ネットワークを切って受話器を上げる | 固まらずに失敗処理を行い、再利用可能になる |
| T-09 | USB受話器を外して起動する | 誤ったデバイスを使わず、エラーを記録する |
| T-10 | 電源を再投入する | 手動操作なしで待機状態へ復帰する |
| T-11 | 連続10回利用する | 前回の会話状態を持ち越さず、各回が終了する |

## 15. 履歴からの方針整理

検討途中では、外部RJ11端子から9V電池とPC817を介してフックとダイヤルを一つの信号として読む案が提示された。その後、教員から黒電話の開封・内部配線の変更が許可されたため、最終設計では内部接点を二つのGPIOへ直接接続する方式を採用した。

同様に、ベル制御も検討されたが、高電圧の交流駆動回路が必要になり初期版の難易度と安全上の負担が増えるため、対象外となった。音声については元の電話回路を使わず、購入済みのUSB-C受話器を移植する方針である。
